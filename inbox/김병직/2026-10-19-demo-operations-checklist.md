## 요약 — 가장 실수하기 쉬운 다섯 가지

1. **카메라에 사람이 조금이라도 보이면 「재실」이다.** 최근 2 s 안에 사람이 한 번이라도 보이면 즉시 재실, 30 s(`P_absent_s`) 동안 안 보여야 부재다 [문서 설계서 §3.4]. vision-node는 사람 점수 원값을 보내고, SafetyCore가 `P_person_score`(0.50, 10/27 D-065 — 그 전 0.35) 이상만 「보임」으로 센다 [문서 `profiles/default.json`, `safety_core/src/policy.cpp` presence 절]. 운영자·관객·촬영자는 물론 포스터·모니터·휴대폰 화면 속 사람도 이 점수를 넘을 수 있다 [추정 — 확인 방법: 3.5절 정리 전후로 3.9절 `empty` 측정의 사람 점수 비교]. 이러면 **M8·M9가 실패한다.** → 2장 시야 경계와 대기 위치.
2. **고양이 잠금은 「사람이 안 보인 시간」이 먼저다.** 새 Core(`c87f8308…` 이후, #168 D-060)는 사람이 `P_cat_absent_s`(10/27부터 **5.0 s**, D-065 — 그 전 4.4 s #174) 동안 안 보이면 고양이 감시를 시작하고, 감시 중 `cat_hit`이 `P_cat_hits`회 이어지면 잠근다. presence(30 s, `P_absent_s`)와는 따로 센다 [문서 설계서 §3.4, #168]. 그래서 인형이 이미 있으면 나간 뒤 **약 6–7 s**(마지막 인식 15:32:40.6–41.6 → 47.6), 사람이 2분 넘게 없을 때 넣으면 넣은 뒤 **1.0 s**에 잠겼다 [실측 2026-10-27 15:30–15:33 Pi 4 정인, #72 6435438156 · 정정 6435488303]. 감시는 사람을 **실제로 마지막 본 시각**부터 센다. 앱 칩 「사람 있음」은 그 뒤에도 2 s(`P_vision_fresh_s`) 남으니, 칩이 꺼지고 약 3 s 뒤 감시가 시작된다 [문서 `safety_core/src/policy.cpp` 162·165–166·176–182행]. 인형을 손으로 놓으면 손이 빠진 뒤부터 세니 **화면 밖에서 집게로 넣는다**(4장 방법 C). 옛 Core `f8164e74`(10/26 18:37 전)는 사람이 마지막으로 보인 뒤 30 s가 지나 부재가 돼야 셌다. 회차마다 7장 「Core 해시」 칸으로 어느 쪽인지 남긴다.
3. **잠금은 사람이 화면에 있어야 풀린다.** 고양이 잠금(M9)은 인형을 **박스 밖까지** 치우고 사람이 화면에 5 s, 위험 잠금(M10)은 위험 해소 10 s + 화면 「위험 확인」 + 재실이다 [문서 §3.4].
4. **Pi 5를 켜면 vision-node를 손으로 시작한다.** `hoodseek-vision-node`·`hoodseek-voice-node` 유닛 모두 `disabled`라 재부팅 뒤 자동으로 뜨지 않는다 [실측 2026-10-26 Pi 5 `systemctl is-enabled`, #67 정인 10/25 「재부팅 뒤 vision-node 수동 기동 필요」]. 3.2절 명령.
5. **측정(3.4절·3.9절)과 서비스는 카메라를 동시에 쓸 수 없다.** 측정 전에 서비스를 멈추고, 끝나면 다시 시작해 `active`를 확인한다(3.9절 `scene_check.sh`는 이것을 스스로 한다). 리허설 회차가 도는 동안에는 멈추지 않는다 — 측정은 회차 사이에 팀에 알리고 한다.

## 3. 시작 전 점검 (매 리허설·시연, 시작 30분 전)

### 3.1 전원·케이블

- [ ] Pi 5는 전용 27 W 어댑터: 라벨 `HT-PD27W-KC`, 정격출력 「5.1V⎓5.0A, 9.0V⎓3.0A, 12.0V⎓2.25A, 15.0V⎓1.8A, 27.0W」 [실측 2026-10-19 라벨 사진]. PD 5 V 5 A 협상, 2분 부하 중 저전압 0 [실측 2026-10-19]
- [ ] LED 판은 별도 어댑터 `XSC-0502000SEKU`(DC 5V 2000mA), 펌웨어 밝기 76/255(≈30 %)·전류 상한 1500 mA, GND만 공통 [실측 2026-10-20 정정인 #48: 3단 + 잠금 링 600 s 이상 없음]. D-036 「≥5 A」에서 바뀌므로 **합의 필요**(#48에서 PM 요청)
- [ ] Pi 4 어댑터: 10/20 현재 `COK-2310`, 정격출력 「5.0Vdc/3,100mA」(USB-A 2구 합계라 다른 기기는 꽂지 않는다) [실측 2026-10-20 라벨 사진, 정정인]. 10분 부하에서 `in0_lcrit_alarm` 0·`dmesg` voltage 0줄로 합격 [실측 2026-10-21 정정인, #64 사전 점검 표]
- [ ] 카메라 USB는 Pi 5에 직접 꽂음(허브 없이). 마이크와 같은 허브면 대역이 겹칠 수 있다 [추정, `inbox/정정인/2026-09-25-wiring-guide.md` §8-D]
- [ ] **Pi 5는 공유기 LAN 포트에 유선, Pi 5 Wi-Fi는 꺼짐, 주소는 Wi-Fi 때 쓰던 고정 주소 그대로**(병직 결정 11/4, #215 6629725199). Pi 4는 Wi-Fi 그대로다. 11/6 현장에도 같은 공유기(병직 11/4, PM #215 질문 6)와 **LAN 케이블**을 가져간다. 유선 21분 동안 끊김 0, 재부팅 뒤에도 유지됐다 [실측 2026-11-04]. M13은 케이블을 뽑지 않고 정인 Mac에서 `iptables`로 Pi 5 주소를 15 s 막는다(4장 M13) — 주소가 같아 대상도 같다
- [ ] **11/6: Pi 5 LAN 케이블을 양쪽 끝에서 테이프로 고정하고, 여분 케이블을 챙긴다** [PM #215 6629825507]. 빠지면 5장 I
- [ ] **이 공유기에는 두 Pi와 Tailscale 마스터 PC(수현 노트북)만 붙인다**(병직 결정 11/4). 운영 PC(병직)와 정인 Mac은 다른 Wi-Fi에 붙고, 마스터 PC를 거쳐(Tailscale `accept-routes`, 위 Tailscale 줄) Pi에 닿는다 — 3.6절 Core 기록과 M13 차단도 이 길로 한다. 그 밖의 휴대폰·노트북은 붙이지 않는다. 마스터 PC가 꺼지거나 이 공유기에서 빠지면 두 노트북은 Pi에 닿지 못한다. 그래도 Pi 4 ↔ Pi 5(앱·vision·음성)는 공유기만 거치니 시연은 계속된다 [추정 — 확인: 마스터 PC를 끈 채 Core 연결 세 개]. 그때만 운영 PC를 이 공유기에 붙이고 `accept-routes`를 끈다. **확인 필요(정인):** Mac에 Tailscale이 있고 `accept-routes`가 켜져 있는지 — 리허설 2 전에 마스터 PC를 거쳐 Core 기록 받기와 Pi 4 ssh를 한 번 해 본다(지금까지는 같은 공유기에서 했다). 11/6 시연장에 두 노트북이 붙을 다른 Wi-Fi가 있는지도 아직 모른다 [추정 — 확인: 현장 안내]. 없으면 휴대폰 핫스팟에 붙여 Tailscale로 닿고, 그것도 안 되면 위처럼 운영 PC만 이 공유기에 붙인다. **두 Pi 주소는 공유기 DHCP 고정 할당에 예약돼 있다** — 11/3 정인이 두 Pi Wi-Fi MAC으로 잡힌 것을 봤고, 11/4 Pi 5 쪽을 유선 MAC으로 바꿨다 [실측 11/4 공유기 관리 화면, #215 6630683599, 정인 #228 리뷰 1]. 예약된 주소는 공유기가 다른 기기에 주지 않으니 마스터 PC·운영 PC가 DHCP로 붙어도 겹치지 않는다. 두 Pi는 기기에서도 주소를 고정했다 [실측 11/4 두 Pi connman `Method=manual`]. **시연 당일에는 공유기 설정을 바꾸지 않는다** — 예약을 바꾸고 「설정 적용」하자 Pi 4 Wi-Fi가 떨어져 4분 넘게 안 돌아와 재부팅했다 [실측 11/4 21:26, #215 6630683599]. Pi 5 유선도 그 순간 51 s 끊겼다(21:26:06–21:26:57, `eth0: Link is Down` → `Link is Up`) [실측 Pi 5 커널 로그, #215 6659422261]
- [ ] 첫 전원 뒤(3.2절 순서) Core 연결 세 개(`hello (ui)·(vision)·(voice)`)가 붙었는지 본다. 공유기를 껐다 켜도 두 Pi 주소와 Core 연결 세 개는 그대로였다 — **공유기 재부팅 뒤 같음** [실측 2026-11-04 21:35:59–21:38:12.9, #215 6630878047]. Pi 5 유선은 공유기가 켜지자 바로 붙었다. Pi 4 Wi-Fi는 켜지는 중인 공유기에 거절당해(`CTRL-EVENT-ASSOC-REJECT status_code=16` → connman `error "not-found"`, `state is failure`) 끊기고 2분 10초 뒤(공유기가 켜지고 74 s 뒤) 다음 시도에서 붙었다. Core는 재시작 없이 앱·음성·vision이 다시 붙었다. 그래서 켜는 순서를 공유기 → Pi 4 → Pi 5로 한다(3.2절). Pi 4가 안 돌아오면 5장 J. 주소는 저장소·이슈에 적지 않는다
- [ ] **Pi 5 케이스 뚜껑이 닫혀 있고, Pi 상자(우드락) 안·옆에 호일·호일로 감싼 인센스 같은 금속이 없다.** 11/3 22:30 Pi 5 옆 호일 감싼 인센스 묶음을 치우고 열린 뚜껑을 닫자(재부팅 없음) Pi 5 → 공유기 300 ms 넘는 지연이 7.7 %(137/1768회, 2 s 넘음 8, 최대 3.75 s) → 0/396회, 전송 실패가 1584/14882 → 0/3157이 됐다 [실측 2026-11-03 #215 6605217767]. 둘을 같이 바꿔 어느 쪽인지는 가르지 않았다. 소품·여분 인센스는 Pi 상자에서 떨어진 곳에 두고, L5 뒤 치울 때도 Pi 상자 쪽으로 가져가지 않는다(정인 소품 동선, #215 6617131200)
- [ ] 운영 PC → Pi 경로: `ip route get <Pi5>`로 본다. Tailscale `accept-routes`가 켜져 있으면 `dev tailscale0`, 곧 마스터 PC(`<마스터 PC>`, 수현 노트북, 항상 켜 둠)를 거쳐 간다 [실측 2026-10-23: Pi 5 ping 손실 0/5, 평균 44.7 ms·최대 150 ms, 마스터 PC까지는 중계 없이 직접 3 ms]. 마스터 PC가 켜져 있으면 그대로 쓴다(10/23 김병직 결정). 마스터 PC가 꺼졌거나 PC → Pi 접속이 끊기면 `sudo tailscale set --accept-routes=false`로 끄고 `dev wlo1`(직접 연결)을 확인한다. 10/21에는 이 경로로 쓰다 접속이 끊겼는데, 선 정리가 안 된 때라 원인을 하나로 정하지 못했다 [추정 — 확인 방법: 끊기면 그 자리에서 `ip route get <Pi5>`와 `tailscale ping <마스터 PC>` 결과를 같이 남긴다]. Pi 4 ↔ Pi 5 연결(L1·L2)은 이 경로와 무관하다
- [ ] 카메라 USB가 끊겼다 붙으면 `/dev/video0`이 `video1`로 바뀔 수 있다 [실측 2026-10-21: `xhci-hcd.1: WARN: buffer overrun event` → `usb 3-1: USB disconnect`, 다시 붙은 뒤 `video1`]. 시작 전 `ssh root@<Pi5> ls /dev/video*`에 `video0`이 있는지 확인. 없으면 카메라를 잡은 프로그램을 끝내고 다시 꽂는다
- [ ] Pi 5 액티브 쿨러가 돌아감

### 3.2 켜는 순서 (제안)

**공유기 → Pi 4 → Pi 5 순서로 켠다**(PM 동의 11/4, #215 6631184366). 켜지는 중인 공유기에 Pi 4가 붙으려 하면 거절당하고 실패 상태로 다음 시도를 기다린다 [실측 2026-11-04 공유기 재부팅 — 3.1절]. Pi 4가 5분 안에 안 붙으면 5장 J.

1. ESP32 2대 전원 → 팬 3단 소리가 나면 정상(부팅 직후 fail-safe) [문서 `CLAUDE.md` 안전 불변식]
2. Pi 4 전원(공유기 다음) → SafetyCore 기동 확인. 유닛이 `disabled`라 전원을 넣은 뒤에는 PC에서 시계를 맞추고 손으로 켠다(아래 Pi 4 명령, 기동 명령은 [문서 `safety_core/README.md`]) [실측 2026-11-04 21:30, #215 6630683599]. 부팅 자동 기동은 #46 — 확인 필요(정정인)
3. Pi 5 전원(Pi 4 다음) → 부팅이 끝나면 아래 명령으로 vision-node 시작
4. voice-node: `systemctl start hoodseek-voice-node`(유닛 `disabled`라 손으로) [실측 2026-10-26 Pi 5 voice journal 15:41:33 `Started`]. **리허설·11/6 기동·확인은 정정인**(실행본 `70839f9c`, `capture_ready`, Core `hello (voice)`, 화자 자리·마이크 점검), 이수현은 ⓖ 음량만 [PM #215 6629825507, 11/4 Slack 결정]. Flutter 앱: 홈 아이콘으로 실행 [문서 `flutter_app/README.md` 「Pi 5에 올리기」, #171 재범 리뷰, #67 정인 10/26 배포 기록: `arc run`은 「Service not found」]
5. 팬이 3단에서 내려오면 Pi 4 → ESP32 명령이 들어가는 것 [추정 — 확인 방법: SafetyCore 로그와 대조]

### 3.6 Core 기록 받기 (회차 시작 전, 새로 10/26)

### 3.7 카메라 카드 영상 확인 (새로 10/26)

- Pi 5에서 `deploy/README.md` 「영상 확인」 줄을 그대로 쓴다(`wget -T 5 … | grep -c 'image/jpeg'`, 1 이상 = JPEG가 실제로 옴).
- `nc … | grep -c hoodseekframe`은 쓰지 않는다. BusyBox `nc`는 HTTP 머리(128바이트)만 받는데 머리에도 `boundary=hoodseekframe`이 있어 영상이 안 와도 1이 나온다 [실측 2026-10-26 Pi 5, `deploy/README.md`].
- 카드 영상은 최대 약 16 FPS, 480×360이다 [문서 #152, UI 설계 v1 §3.2]. 화면 뒤의 판정 속도(약 3.3~3.5 FPS [실측 10/26 #67 배포 기록])와는 다르다.
- [ ] **앱 말고 영상 접속이 없는지.** 영상 서버는 동시에 2곳까지만 받고 그 뒤 접속은 바로 닫는다 [문서 `vision_node/src/preview.cpp` 28행 `kMaxViewers = 2`]. E2E 3회차(10/27 14:16)에 위 `wget` 확인이 0이 나왔는데, 앱 카드 한 자리와 11:21경부터 열린 SSH 터널(`dropbear`) 한 자리로 차서 확인 접속만 밀려난 것이었다. 앱 카드는 영상을 받고 있었지만, 그 상태로 앱을 다시 켜면 옛 연결이 정리될 때까지 카드가 빌 수 있다 [실측 10/27 14:16 병직, Pi 5 `netstat -tnp` 읽기만 — 이슈에는 남기지 않았음]. 시작 전에 아래가 `1`(앱만)인지 보고, 2면 `netstat`으로 누가 붙었는지 봐서 앱이 아닌 연결을 닫는다

```bash
# (Pi 5, 읽기만) 영상 서버(7431 = 0x1D07)에 붙은 연결 수. 앱만이면 1. 위 wget 확인을 하는 동안은 잠깐 2
awk '$2 ~ /:1D07$/ && $4 == "01"' /proc/net/tcp | wc -l
# 누가 붙었는지: 상대 주소가 127.0.0.1:7431인 줄의 프로그램 이름(앱은 hood_seek)
```

### 10.1 카메라 USB 분리 시험 (F7, 사무실에서 5분 — 10/23 끝남)

카메라 USB를 손으로 뽑아야 해서 원격으로는 못 한다. `live_view.py` 같은 다른 카메라 프로그램은 모두 끈 상태에서 한다.

```bash
# (내 PC) Pi 5 접속
ssh root@<Pi5>

# (Pi 5) 서비스 시작 → active
systemctl start hoodseek-vision-node
sleep 5; systemctl is-active hoodseek-vision-node

# (Pi 5) 분리 전 기록: NRestarts 값과, index0이 ../../video0을 가리키는지 (index1 -> video1은 메타데이터 장치라 정상)
systemctl show hoodseek-vision-node -p NRestarts
ls -l /dev/v4l/by-id/

# (손) 카메라 USB를 뽑는다. 아래 명령으로 10초 기다린 뒤 같은 포트에 다시 꽂는다
sleep 10

# (Pi 5) 꽂고 나서 10초 뒤 확인
sleep 10
ls -l /dev/v4l/by-id/
systemctl is-active hoodseek-vision-node
systemctl show hoodseek-vision-node -p NRestarts
journalctl -u hoodseek-vision-node -n 5 --no-pager
```

| 결과 | 판정 | 다음 일 |
|---|---|---|
| `…-video-index0 -> ../../video0`, `active`, NRestarts가 늘었고 journal 마지막 줄에 `cannot open camera device`가 없음 | 통과 (저절로 복구) | F7 수정 안 함. 결과를 이 표 3번에 [실측]으로 적음 |
| `-> ../../video1`(또는 다른 번호), journal에 `cannot open camera device: /dev/video0`가 반복 | 실패 | 카메라를 다시 꽂아 `video0`으로 되돌린 뒤, 결과를 근거로 `deploy/` 코드 소유자(정정인·남현지)에게 서비스가 고정 경로(`/dev/v4l/by-id/…-video-index0`)로 카메라를 열게 하는 PR을 요청 |
